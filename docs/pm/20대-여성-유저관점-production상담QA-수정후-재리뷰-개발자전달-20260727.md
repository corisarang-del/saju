# 20대 여성 유저관점 production 상담QA 수정후 재리뷰 개발자 전달

## 배경
- 2026-07-27 기준 production 상담 QA 수정 후 20대 여성 유저 관점 재리뷰가 진행됐다.
- 소스코드는 리뷰 과정에서 수정하지 않았다.
- 최신 수정의 방향은 좋지만, 실제 production 유료 전환 준비도는 아직 완전 합격이 아니다.
- 이번 문서는 개발자가 다음 수정과 QA를 진행할 때 사용할 작업 기준이다.

## 총괄 PM 판단
- 무료 3회 상담 사용 의향은 `9.4/10`으로 높다.
- `10별 2,900원` 스타터 결제 의향은 `8.4/10`이다.
- `월 9,900원 / 50별` 구독 의향은 `7.1/10`이다.
- 상담 품질 코드 기준 준비도는 `8.5/10`이다.
- 실제 production 유료 전환 준비도는 `7.2/10`이다.

## 핵심 결론
- 이번 수정은 상담 신뢰를 올리는 방향으로 맞다.
- live QA 스크립트가 앱의 최신 초기 프롬프트 source of truth를 따라가게 된 점은 중요하다.
- 구버전 첫 질문도 첫 상담 품질 게이트를 타게 한 점은 실사용 안정성에 좋다.
- 캐릭터별 fallback opening과 행동 구조를 분리한 점은 유료 전환에 긍정적이다.
- 하지만 최신 수정 배포 후 production live QA 통과 기록이 아직 없고, 직전 응답 시간이 `37.9초~52.9초`라 속도가 가장 큰 잔여 리스크다.
- 결제는 계속 닫아둬야 한다. 유료 오픈은 production live QA와 응답 시간 개선 확인 뒤 판단한다.

## P0. 최신 수정 배포 후 production live QA 재실행

### 문제
- 코드와 테스트 방향은 좋아졌지만, 최신 수정이 production에서 실제로 통과했는지 아직 확인되지 않았다.
- 이전 재검증에서는 `scripts/qa-live-api-check.mjs` free-only/full 시나리오가 실패했고, 구버전 첫 질문과 source of truth 불일치가 원인으로 보였다.

### 요구사항
- 최신 배포 후 production 기준으로 free-only live QA와 full live QA를 다시 실행한다.
- live QA 스크립트는 앱의 최신 초기 프롬프트 source of truth를 사용해야 한다.
- 최신 클라이언트뿐 아니라 구버전 첫 질문도 첫 상담 품질 게이트 또는 안전 fallback을 타야 한다.

### 수용 기준
- `QA_SCENARIO=free-only` production live QA가 `ok: true`로 통과한다.
- full production live QA가 `ok: true`로 통과한다.
- 무료 첫 상담, 별 지급/차감, 거래 로그, assistant 저장, `chat_used` 증가가 실제 DB 기준으로 일관된다.
- 구버전 초기 질문에서도 마지막 질문, 오늘 행동, 쉬운 말, 2문단 기준을 만족한다.
- 실패 시 원인이 스크립트/프롬프트/API/DB/provider 중 어디인지 로그로 구분된다.

## P0. 7개 캐릭터 반복 QA

### 대상
- 현우
- 하나
- 민준
- 인영
- 지안
- 서준
- 도윤

### 요구사항
- 7개 캐릭터를 각각 최소 3회 이상 반복 QA한다.
- 단순 HTTP 200만 보지 말고 저장된 assistant 품질까지 확인한다.
- 캐릭터별로 fallback 여부와 latency를 함께 기록한다.

### 확인 항목
- HTTP 200
- assistant 메시지 저장
- 무료 횟수 또는 별 차감 정합성
- 거래 로그 정합성
- 정확히 2문단 또는 허용된 첫 상담 문단 수
- 마지막 질문 1개
- 오늘 할 행동 포함
- 한자/전문용어 과다 없음
- `아웃풋` 같은 어색한 외래어 없음
- 반말 캐릭터의 존댓말 혼합 없음
- 캐릭터별 말투와 관점 차이 확인

### 수용 기준
- 각 캐릭터 3회 반복에서 치명 실패가 없어야 한다.
- 인영은 한자/전문용어 초반 몰림이 재발하지 않아야 한다.
- 도윤은 503 또는 50초대 timeout이 재현되지 않아야 한다.
- fallback이 발생해도 캐릭터별 말투와 분야가 유지되어야 한다.

## P1. 첫 상담 응답 속도 개선

### 문제
- 직전 production QA에서 7명 캐릭터 응답 시간이 `37.9초~52.9초`였다.
- 20대 여성 유저 기준 첫 답변이 40초를 넘으면 앱이 멈춘 것처럼 느껴지고, 2,900원 스타터 결제 의향도 떨어진다.

### 목표
- 첫 의미 있는 표시: 15초 안쪽
- 전체 첫 상담 완료: 30초 안쪽
- 30초 초과 시 사용자가 실패로 오해하지 않는 진행 안내 제공

### 요구사항
- live QA 결과에 latency를 필수로 남긴다.
- provider timeout 여부와 fallback 진입 여부를 필수로 남긴다.
- fallback 비율이 높으면 fallback 문장 개선보다 provider 호출/timeout/재시도 전략을 먼저 본다.
- 25초 timeout 후 안전 fallback을 쓰는 정책이 실제 production에서 체감 지연을 줄이는지 확인한다.

### 수용 기준
- 캐릭터별 p50 응답 시간이 30초 안쪽이다.
- 캐릭터별 p95 응답 시간이 운영자가 볼 수 있게 기록된다.
- 30초 초과 케이스는 request id와 원인 분류가 남는다.
- fallback 응답도 품질 게이트를 통과하고, 사용자에게 템플릿처럼 반복 노출되지 않는다.

## P1. 캐릭터별 fallback 반복감과 말투 차별화 보강

### 문제
- fallback이 개선됐더라도 실제 provider가 자주 fallback으로 빠지면 유저는 깊은 상담보다 안전한 템플릿으로 느낄 수 있다.
- 여러 캐릭터가 비슷한 opening을 반복하면 "어차피 다 같은 AI 답변"처럼 보인다.

### 요구사항
- 캐릭터별 opening pattern을 명확히 분리한다.
- 캐릭터별 마지막 질문 방식도 분리한다.
- fallback도 캐릭터별 toneProfile을 따라야 한다.
- 문장 오류와 어색한 조사를 자동 QA에 계속 추가한다.

### 캐릭터별 기대
- 현우: 핵심 판단과 오늘 행동을 짧게 정리하되 겁주지 않는다.
- 하나: 감정 속도와 표현 방식을 부드럽게 잡는다.
- 민준: 돈 구조와 이번 달 기준을 생활 언어로 말한다.
- 인영: 시기와 준비 행동을 쉬운 말로 나눈다.
- 지안: 재회 가능성보다 연락 기준과 감정 소모를 차분히 본다.
- 서준: 버틸 조건과 움직일 조건을 현실적으로 나눈다.
- 도윤: 사람, 돈, 시기 리스크를 과장 없이 정리한다.

### 수용 기준
- 같은 고민을 2명 이상 캐릭터에게 물었을 때 첫 문단 구조가 달라야 한다.
- 캐릭터별 답변 말투가 QA 표에서 구분되어야 한다.
- `지금은 지금`, `관계의 거리을`, 반말/존댓말 혼합 같은 문장 오류가 재발하지 않아야 한다.

## P1. 20대 여성 유저 기준 결제 전환 판단 QA

### 요구사항
- 무료 3회는 계속 열어둔다.
- 결제는 Paddle env와 signed webhook live QA가 닫히기 전까지 열지 않는다.
- 2,900원 스타터는 첫 답변 품질과 속도가 확인된 뒤 전환 테스트 대상으로 본다.
- 월구독은 첫날 결제보다 며칠 사용 뒤 판단하는 흐름으로 설계한다.

### 판단 기준
- 첫 답변이 30초 안에 온다.
- 첫 답변이 내 고민을 생활 언어로 잡아준다.
- 후속 질문에서 이전 말을 기억한다.
- 오늘피드와 월간 리포트가 반복 사용 이유를 만든다.
- 결제 전에는 `돈 내도 느릴 것 같다`는 불안을 만들지 않는다.

## QA 산출물
- latest production free-only live QA 결과
- latest production full live QA 결과
- 7개 캐릭터 x 3회 반복 QA 표
- 캐릭터별 latency 표
- fallback 발생률 표
- provider timeout/error 로그 요약
- 캐릭터별 첫 답변 캡처
- 문장 오류/외래어/말투 혼합 재발 목록

## 개발 우선순위
1. 최신 수정 배포 후 production free-only/full live QA를 다시 돌린다.
2. 7개 캐릭터를 각각 3회 이상 반복 QA한다.
3. 첫 의미 있는 표시 15초, 전체 완료 30초 목표로 latency를 측정한다.
4. fallback 비율과 provider timeout 원인을 기록한다.
5. fallback 반복감과 캐릭터별 opening 차이를 보강한다.
6. 결제는 계속 닫아두고, Paddle production env와 signed webhook QA가 닫힌 뒤에만 유료 전환 테스트를 검토한다.
